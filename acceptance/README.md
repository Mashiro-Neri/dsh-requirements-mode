# 验收工作流

这个目录回答一个问题：**怎么证明它真的做完了**。不看代码写完没有，只看真实副作用和可复核的证据。

## 文件

- `README.md`（本文件）：流程、判定规则、禁止事项
- `ACCEPTANCE_PLAN.md`：验收计划模板，复制成 `验收计划.md` 填写
- 证据卡模板：实现契约目录下的 `templates/EVIDENCE.md`（本包里是 `contract/templates/EVIDENCE.md`）。交付时契约会被复制到 `03-验收/实现契约/`，证据卡复制成 `03-验收/证据卡.md`。

## 流程

1. **定风险级别**：每个范围标 L0–L3；命中迁移/鉴权/部署/密钥/数据/配置最低 L2，删除与不可逆最低 L3，拿不准升一级。L2/L3 必须有用户原话确认。
2. **写验收矩阵**：每条写成 `操作/命令 → 期望可观察结果 → 环境 → 通过阈值`。覆盖正常、空态、加载、失败、权限不足、超时、无人在场、未知结果、断网、重启、跨版本、性能 p50/p95、缓存真实命中、审计。
3. **定义状态语义**：`状态 / 原因码 / 是否可重试 / 用户是否在场 / 用户文案 / 模型文案 / 审计记录`；副作用另加 `approval_state`、`effect_state`、`retryable`、`idempotency_key`、`unknown_outcome`。
4. **取证**：原始命令输出（含 exit code、时间、环境）→ 日志/事件序列 → 带目标身份的真机截图 → 可重复脚本 → 失败注入记录。证据放 `evidence/<task>/<commit>/`，原样保留，不改写。
5. **独立判定**：`verified` 只能由独立验证者写；实现者最高 `demo`。用户可见的变更还要用户自己看到结果并留下原话，否则最多 `awaiting-user`。
6. **归档**：把计划、证据、判定结论一起随交付物打包，别只留一句"其余正常"。

## 不适用的行

写 `N/A + 原因`，由复核者确认。不要空着，也不要静默跳过。

## 禁止

- 接口 200、单测绿、日志出现 `started` 当成完成
- 只看单测或只看截图局部
- 用自算 hash 冒充缓存命中
- 用"应该可以"代替真机
- 失败或取消路径没测就宣布通过
- 把未验证项合并成一句"其余正常"

## 和需求确认的关系

- 常规路线：默认一份开发文档；**内容确实写不下**时才拆第二份（通常是验收或附录），不要为了凑份数预先拆。
- 大型项目路线：`03-验收/` 里放本文件的副本、填好的验收计划和证据卡；实现契约默认随包提供，放在 `03-验收/实现契约/`。
