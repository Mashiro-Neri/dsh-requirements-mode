# 需求规划文档 · 大型项目（可复用模板）

> status: living · last-reviewed: 2026-11-01 · owner: lead
> 用途：把“用户的一个想法”推进到“可开工的边界、契约、阶段和验收”。
> 这不是最终开发文档，也不是架构定稿；它负责把不确定性收敛到可以决策。

## 0. 开发 AI 使用说明

> **开发 AI 使用说明**：本文档记录了与用户讨论后形成的目标、偏好和当前建议，仅作为开发依据与决策上下文，不应被盲目视为绝对正确、完整或不可变的事实。开发前及开发中，应结合实际代码库、运行环境、目标系统、官方文档与可执行测试验证关键假设。若发现本文档与实际情况、接口限制、性能表现或更合适的实现方案不一致，应说明差异、给出可行选项，并与用户讨论后再决定；不要默默偏离已确认的用户体验，也不要为了机械遵守文档而采用已验证不合适的实现。

## 1. 适用场景

适用于：

- 需求跨越多个系统/设备/角色
- 用户只有一个方向，没有完整规格
- 旧系统已经有大量可复用能力
- 需要同时考虑上下文、缓存、权限、离线、性能
- 一旦做错，返工成本很高

不适用于：

- 单文件 bug 修复
- 目标、输入输出、验收都明确的小功能
- 只需要直接写代码的局部改动

## 2. 总流程

```text
意图 → 现实核查 → 概念定义 → 不变量 → 深度推翻/多角色红队
→ 状态语义 → 拆分 → 决策冻结 → 最小验证 → 分阶段实现
```

| 阶段 | 要回答 | 产物 | 闸门 |
|---|---|---|---|
| 1 意图 | 用户到底要什么、不要什么 | 需求意图摘要 | 用户复述确认 |
| 2 现实核查 | 现有系统已经有什么、拒绝过什么 | 能力盘点 + 冲突清单 | 不再重复造轮子 |
| 3 概念 | 每个词到底指什么 | 术语表 + 反例 | 用户能用自己的话复述 |
| 4 不变量 | 什么绝对不能破坏 | 不变量清单 | 可逐条验收 |
| 5 红队 | 换角色会怎么失败 | 多角色审查报告 | 高风险项有处理 |
| 6 状态语义 | 失败/等待/未知怎么表达 | 状态机 + 文案表 | 模型/用户/审计都能理解 |
| 7 拆分 | 哪些先做、哪些不做 | 阶段计划 + kill list | 先证明核心闭环 |
| 8 冻结 | 哪些决定已经定死 | ADR/决策台账 | 用户明确接受 |
| 9 验收 | 怎么证明真的成立 | 真机验收清单 | 证据可复核 |

## 3. 阶段 1：意图

不要从“技术方案”开始。先写：

```text
用户原话：
他真正想完成的任务：
现在怎么做的：
为什么现有方案不够：
成功时用户会看到/感觉到什么：
明确不做：
已知约束（预算/设备/隐私/时间）：
```

把信息分成四类，禁止混写：

- 已确认项：用户明确说过
- 用户偏好：倾向，但可变
- 技术建议：AI 建议，不是用户决定
- 待确认项：会影响方向的不确定性

### 关键动作

- 用非技术语言复述一次，问“我理解得对吗”
- 给一个具体使用场景，而不是抽象目标
- 找出“用户嘴上说想要”和“真正每天会用”的差异
- 明确非目标；没有非目标的大项目一定膨胀

## 4. 阶段 2：现实核查

大项目最常见的浪费：把已经存在的能力重新设计一遍。

先查：

- 现有代码/数据库/协议
- 旧 ADR/设计文档
- 已验收功能
- 已明确拒绝的方案
- 是否已有 lease/outbox/审批/缓存/事件账本

输出一张表：

| 能力 | 已存在？ | 现有语义 | 差距 | 处理 |
|---|---|---|---|---|
| 会话同步 | 是 | 轮次边界 + SSE | 执行者不同 | 收口，不重造 |
| 离线 | 是 | outbox + 冲突三选一 | 无分支 UI | 复用 |
| 跨设备工具 | 部分 | 仅 UI/API 发起 | 模型不能驱动 | 新 ADR |

### 审计 Agent 提示词模板

```text
你是独立架构/需求审计员。只读，不修改文件。
目标：找出这个方案中“已经存在却被当成新增”“与现有 ADR 冲突”
“会造出第二套事实源”“安全边界被绕过”“过度设计”的地方。
请按 P0 阻断 / P1 设计缺口 / P2 可删复杂度输出，
每条给代码/文档路径与行号证据；区分事实、推断、建议。
不要只评价好坏，要给出最小可行修正。
```

审计报告不是结论，必须由 Lead 逐条处理：接受 / 驳回 / 交用户裁决。

## 5. 阶段 3：概念定义

每个核心词必须给三个东西：

```text
日常比喻：
系统定义：
反例（它不是什么）：
```

例：

- 执行权：谁拿麦克风，不是模型本身
- Runner：当前替 Sora 跑模型的服务
- ContextManifest：配方回执，不是整锅菜
- 项目卡：档案，不是记忆
- 缓存作用域：哪个厨房的备菜，不是浏览器缓存

术语不定清楚，后面所有讨论都会在不同含义上打架。

## 6. 阶段 4：不变量

大项目不要先画完整架构，先写不可破坏的规则。

建议覆盖：

- 身份：谁是同一个自己，什么算分支
- 权威：唯一事实源在哪
- 上下文：稳定前缀怎么生成，什么只能进尾部
- 缓存：同一缓存域的条件
- 状态：等待/未知/失败/拒绝怎么区分
- 副作用：幂等、重试、补偿
- 权限：谁能批准、谁能执行
- 离线：断线后什么继续、什么停止
- 性能：非模型开销预算
- 安全：密钥、设备信任、攻击面

每条不变量都要能写成验收项，而不是口号。

## 7. 阶段 5：深度推理、自我推翻与多角色红队

### 7.1 先分清探索和收敛

- **探索期**：允许不断提出新架构、反方案、极端假设
- **收敛期**：必须把方案收敛到可冻结的契约

不能一边探索一边写代码；也不能只探索不收敛。

### 7.2 自我推翻循环

每个关键决策至少走一轮：

```text
1. 复述当前方案和隐含假设
2. 生成至少 2 个反方案/替代路径
3. 对每个方案做 pre-mortem：假设半年后失败，列出原因
4. 找反例、边界、最坏情况
5. 记录“为什么推翻/为什么保留”
6. 修订方案或建立分支
7. 交给独立审查者（新上下文/新角色）再审
8. 没有新增 P0/P1 阻断问题，才允许收敛
```

允许“推翻重来”，但每一次推翻都要留下台账，不能只是感觉“这个不好”。

### 7.3 反方案台账

```text
| 编号 | 原方案 | 反方案/推翻理由 | 反例或失败场景 | 证据 | 结论 | 什么条件下可复活 |
```

结论只能是：

- active：当前采用
- rejected：已否决
- dormant：暂不采用，保留
- revived：条件变化后重新启用

### 7.4 收敛标准

“挑不出毛病”不可证明；可验证的收敛标准是：

- 没有已知 P0/P1 阻断问题
- 所有不变量都能被验收
- 关键假设有证据，或明确标为 unknown
- 八个视角都要发声；同一 Agent 可以切换，不要求新建八个代理
- 剩余风险被显式列出并由用户接受
- 连续两次独立审查没有新增阻断问题
- 至少完成一次完整 pre-mortem
- 反方案台账没有未解释的 rejected

达不到就继续推演；但同一问题最多三轮，之后必须：

- 降级为 known risk
- 或交用户裁决
- 或明确标记“当前无法验证”

不允许无限循环来伪装确定性。

### 7.5 多视角红队（不是多代理）

至少用这八个视角各审一遍：

| 角色 | 必问 |
|---|---|
| 用户 | 会不会突兀、卡住、不知道发生了什么 |
| 设计师 | 状态是否可读，等待/失败/离线是否画错 |
| 全局架构 | 权威源是否唯一，协议是否可重放 |
| 安全 | 模型能否自批，审批能否伪造，prompt injection 路径 |
| 混沌工程 | runner 崩溃、设备拔出、丢包、重复执行 |
| 成本 | 缓存是否真命中，记忆/项目卡是否 token 爆炸 |
| 维护者 | 是否又造一层，是否复用现有 lease/outbox |
| 反方案者 | 这个方案最可能在哪种场景下完全错 |

角色是**视角**，不是代理数量。
默认由同一个 AI 依次切换视角，输入相同、问题不同。
只有安全、混沌工程等高风险视角，才建议另起独立 reviewer 复核，避免自己审自己。

每个视角都必须给出具体失败场景和证据，不能只写“已考虑”。

输出：

```text
角色：
最担心的失败：
证据/场景：
建议修正：
是否阻断：
```

禁止只让一个视角通过就宣布方案完成。

## 8. 阶段 6：状态语义

大项目最容易漏的不是正常流程，是“没有用户/超时/未知结果”。

统一结构：

```text
状态
原因码
是否可重试
用户是否在场
用户文案
模型文案
审计记录
```

基本规则：

- 无人在场 ≠ 用户拒绝
- 超时 ≠ 用户拒绝
- 未知结果 ≠ 失败
- 设备离线 ≠ 文件不存在
- 审批未送达 ≠ 策略拒绝
- 没开始执行 ≠ 已执行

副作用必须单独建模：

```text
approval_state
effect_state
retryable
idempotency_key
unknown_outcome
```

## 9. 阶段 7：拆分

拆分顺序：

```text
0. 契约/ADR
1. 最小上下文一致性
2. 执行权/传输
3. 设备与动作
4. 记忆/项目
5. 自进化/主动性
```

原则：

- 先证明最小闭环，再铺功能
- 先契约，后 UI
- 一个阶段只回答一个问题
- 每阶段有独立验收
- 先写 kill list：现在明确不做什么

### 依赖顺序检查

- 如果身份/上下文没定，先做项目卡 = 建在沙子上
- 如果审批没定，先做跨设备写 = 安全债
- 如果缓存没定，先做多端 = 假同步
- 如果回滚没定，先做自进化 = 人格漂移

## 10. 阶段 8：决策冻结

每个难回头决定写 ADR：

```text
背景
决定
备选及不选原因
代价/风险
重审触发器
关联文档
```

状态：

- proposed：已讨论，未冻结
- accepted：用户确认，可实施
- superseded：被新 ADR 取代

规则：

- 一条 ADR 只做一个决定
- 不改 old ADR，写新的 supersede
- 决策台账记录“用户哪次确认”
- 任何与旧 ADR 冲突的地方必须显式说明

## 11. 阶段 9：验收

验收必须包含：

- 正常路径
- 空态/加载/失败/权限不足
- 超时/无人在场/未知结果
- 断网/重启/重连
- 跨设备/跨构建版本
- 性能 p50/p95
- 真实缓存命中
- 审计证据

证据形式：

- 原始 usage JSON
- 两端 ContextManifest
- 日志/事件序列
- 真机截图
- 可重复脚本
- 失败注入记录

禁止：

- 只看“代码写完”
- 只看单测
- 只看截图
- 用自算 hash 冒充缓存命中
- 用“应该可以”代替真机

## 12. 可复用文档骨架

复制到 `requirements/<项目名>-需求规划文档.md`，按阶段填写：

```text
0. 开发 AI 使用说明
1. 背景与一句话目标
2. 用户场景与日常使用
3. 已确认项 / 用户偏好 / 技术建议 / 待确认项
4. 非目标与 kill list
5. 现有系统能力盘点
6. 术语表（比喻/定义/反例）
7. 不变量清单
8. 架构总图与五个平面
9. 核心契约（配置/上下文/状态/权限/缓存）
10. 关键流程与状态机
11. 失败/等待/未知语义矩阵
12. 深度推理/自我推翻/多角色红队报告 + 反方案台账
13. 分阶段计划与依赖
14. ADR/决策台账
15. 真机验收与证据
16. 风险、重审触发器、未决项
```

## 13. 本次 Sora 案例复盘

### 起点

用户提出：

- 所有设备共享一个上下文
- 模型在哪里操作，意识就在哪里
- 身体可热插拔
- 项目完成后变成项目卡
- 人格可以成长，但不能漂移

### 过程中的关键转折

1. 最初把“意识切换”理解为 host handoff
2. 修正为“共享上下文 + 分布式执行”
3. 审计发现大量已有能力（lease/outbox/审批/同步），不能重造
4. 发现“前缀字节一致”不等于缓存命中，还要账号/模型/凭据/TTL
5. 发现“无人在场/超时/未知结果”必须有独立语义
6. 发现“内部网络”不能当作无攻击面，砍签名但不砍 TLS/鉴权
7. 最终冻结为 6 份 ADR + 分阶段验收

### 最大教训

- 大项目真正的风险不是功能少，而是**事实源分裂**
- 先定义“什么算同一个自己”，再谈多设备
- 先定义失败语义，再谈自动化
- 先证明缓存/上下文，再谈项目卡和自进化
- 不能让所有角色都用同一个乐观假设
- 推翻重来不是无限循环；用反方案台账 + 收敛标准结束探索

## 14. 交付前检查清单

- [ ] 用户能用非技术语言复述目标
- [ ] 有四类信息分离，没有把建议写成已确认
- [ ] 现有能力已盘点，明确“收口 vs 新造”
- [ ] 核心术语都有比喻 + 定义 + 反例
- [ ] 不变量可逐条验收
- [ ] 八个视角都审过（同一 Agent 切换即可；高风险单独复核），包含反方案者
- [ ] 至少完成一次 pre-mortem
- [ ] 有反方案台账与推翻记录
- [ ] 满足收敛标准（无 P0/P1、两次独立审查无新增阻断、剩余风险显式）
- [ ] 审批/超时/无人在场/未知结果有状态
- [ ] 有 kill list
- [ ] 有 Phase 0 契约和最小验证
- [ ] 有 ADR/决策台账
- [ ] 有真机验收与证据格式
- [ ] 没有“文档写完就直接开工”的默认路径
