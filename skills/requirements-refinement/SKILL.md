# 阶段 A/B、真机调查与一致性维护

## 一、阶段 A：理解需求与可行性

1. 先**复述**你对用户目标的理解，问是否准确——不要跳过这一步直接给方案。
2. 再说明主要实现路径、可行性与限制：
   - 有没有官方 API、稳定文件格式或成熟集成？
   - 是否涉及登录、授权、敏感数据、付费资源或第三方服务？
   - 是否存在短期可用但长期脆弱的方案？
   - 用户是否只是在了解，而不是要求立即行动？
3. 比较维度：稳定性、维护成本、上手难度、资源占用、隐私、长期风险。

## 二、阶段 B：确定日常使用体验

围绕"用户每天如何使用它"提问，而不是只问视觉风格：

| 维度 | 要确认的内容 |
|---|---|
| 形态 | 常驻、托盘、置顶、置底、自动隐藏、启动状态 |
| 交互 | 只读、编辑、快捷操作、手动刷新、快捷键 |
| 内容 | 展示范围、筛选、排序、状态、空态、异常态 |
| 外观 | 信息密度、直角或圆角、字体、主题、颜色、图标、布局 |
| 个性化 | 位置、尺寸、记忆、锁定、设置入口 |
| 使用环境 | 账户、设备、屏幕、网络与性能限制 |

可以用简短文字草图或表格帮用户确认，但必须说明它们是**讨论示意，不是最终视觉稿**。

## 三、真机调查

凡是"这台机器/这个代码库实际上是什么样"的问题，交给 `subagent_explore`，不要猜、不要用常识补全。

它是一次创建、反复派活的持久子 agent：第一次用 `subagent_explore` 创建并把背景讲清（它看不到本次对话，**背景只讲这一次**），之后每轮用 `send_message` 派具体任务，每轮仍要写清那一轮的问题与调查计划。

台账里记这类事实时，`来源` 写"调查员带回的命令与输出"，并保留原始命令。调查员标注为"推断"或"未能确认"的，进台账时降级为待确认项，不得当成已确认项。

涉及真机调查的会话，主动请用户在 `/permission` 里切成 read-only。工具面已经拿掉写工具，但沙箱只覆盖文件操作，网络与进程不在它的词汇里；会话沙箱是唯一的物理兜底。

### 沙箱与真机的关系

DSH 沙箱在 Windows 上是**同一台机器上的受限执行**，不是虚拟机或容器。所以操作系统、已装软件、运行时版本、PATH、环境变量、真机文件内容都一样；**不一样的只有两样**：能读写的范围被限制在工作区，以及 read-only 下 pwsh 跑在 ConstrainedLanguage 模式（`.NET` 静态调用、`Add-Type`、COM、反射会以 "only core types" 失败）。

由此：

- 纯逻辑测试（纯计算、不写盘）：环境一致，沙箱里能跑。
- 只读命令、版本/路径/日志/进程/端口：本来就该在沙箱里做。
- **任何要写盘的测试**（写临时文件、生成 build 产物、跑框架脚手架）：不要在本阶段做，会被沙箱挡住或污染用户工作区。
- 需要网络下载依赖的测试：与沙箱无关（沙箱只覆盖文件操作），但同样不属于本阶段。

**关键提醒**：调查员报回的命令失败，未必等于方案不可行。read-only 下的语言级别限制会造成假阴性——要在报告里区分"事实如此"和"命令被沙箱挡住了"。

## 四、变更同步：改一处要查所有受影响区域

用户修改一个细节时，不要只改一处，要扫一遍连带影响。以"标题栏的『隐藏』按钮改成『刷新』"为例，至少同时更新：

- 标题栏按钮本身
- 图标 / SVG 素材清单
- 手动刷新的**成功**与**失败**表现
- 原"隐藏"功能的**新入口**
- 相关文字草图
- 完成标准里对应的验收项

每次修改后，向用户简短说明**改动 + 连带影响**，避免文档自相矛盾。

更一般的方法：把文档按"条目"组织（每个已确认的交互/状态是一条），改动时先问"这条还被谁引用"，再逐处收敛。
