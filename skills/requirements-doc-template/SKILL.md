# 最终开发文档的骨架与交付自检

只有在用户明确表达"方向确认""可以整理开发文档""按这个写给 AI"之后才使用本技能。产出文档后即停止，不默认进入实现。

## 一、开头固定段落（原文照抄，或保留等价含义）

> **开发 AI 使用说明**：本文档记录了与用户讨论后形成的目标、偏好和当前建议，仅作为开发依据与决策上下文，不应被盲目视为绝对正确、完整或不可变的事实。开发前及开发中，应结合实际代码库、运行环境、目标系统、官方文档与可执行测试验证关键假设。若发现本文档与实际情况、接口限制、性能表现或更合适的实现方案不一致，应说明差异、给出可行选项，并与用户讨论后再决定；不要默默偏离已确认的用户体验，也不要为了机械遵守文档而采用已验证不合适的实现。

## 二、文档骨架

1. **项目背景、产品目标与非目标**——先说清要解决什么问题，以及明确不做什么。
2. **已确认的用户体验与视觉方向**——用户可感知的目标和验收结果放前面。
3. **主界面、交互状态、设置与常用操作设计**——含空态、加载、失败、权限不足、配置缺失等状态。
4. **数据、授权、同步、缓存与隐私边界**——数据从哪来、写到哪去、谁能看、失败怎么办。
5. **用户需提供的素材、配置或账号信息**——谁在什么时候提供什么，缺失时如何降级。
6. **技术建议与取舍**——写清理由、代价与替代方案，不伪装成定稿，不作为无必要的硬约束。
7. **待确认项或开发时可自行决定的内容**——把用户尚未决定的和不影响产品目标的内部实现问题分开列。
8. **可验证的完成标准**——每条都要能观察、能验证。

## 三、表述原则

- 对体验目标用"应当""优先""不要"；仅对不可妥协的要求用"必须"。
- 技术选型写清理由与替代方案，不因方便而固定单一框架、目录结构、类名、依赖版本或缓存格式。
- 不凭空增加用户没有讨论过的功能。
- 明确素材依赖：例如用户希望自行提供图标素材时，写出"开发 AI 应在图标实现阶段主动索取"，并注明不得自行下载替代。

## 四、交付前自检

- [ ] "已确认项"每一条都能追溯到一次真实的用户答复（问题 id 或对话轮次）。
- [ ] 没有把自己的建议、默认假设或技术偏好写进"已确认项"。
- [ ] 四类信息（已确认项／用户偏好／技术建议／待确认项）彼此分开，没有混写。
- [ ] 每组模糊词（简单、实时、好看、轻量、自动）都有可观察定义。
- [ ] 权限、成本、稳定性、资源占用、隐私与失败行为，凡涉及者均已写。
- [ ] 主界面草图或表格已标注"讨论示意，非最终视觉稿"。
- [ ] 变更同步已核过：本轮改动牵动的其他小节都已一并更新。
- [ ] 文档结尾没有"接下来我开始实现"这类默认进入实现的表述。
- [ ] 已经过 `subagent_review` 复核，且报告里的每一条都有明确处理结论（接受／驳回／上报用户）。

## 五、交付前复核（硬环节，不可跳过）

顺序不能颠倒，尤其**不要在复核前落盘**：

1. 先按上面的骨架写出**草稿**，只在对话里给用户看。
2. 加载本技能，并用它自检一遍。
3. 调用 `subagent_review`，一次把四样东西交全：
   - 草稿全文（它是独立子 agent，**看不到本次对话**，不贴等于没给它材料）
   - 用户的原话要点（尤其是"已确认项"各自对应哪次答复）
   - 你的确认台账
   - `subagent_explore` 带回的真机事实（含原始命令与输出）
4. 拿到报告后**先对话，再回报用户**：
   - 报告里的"待澄清"和误判，用 `send_message`（本 preset 自带，target 用复核者返回的 childId）把你能给的具体依据（用户原话、当时的选择、现场约束）告诉它。它必须逐条回"撤回（理由成立）"或"维持（缺的是 X）"。
   - **给它理由，不要只坚持结论**。拿不出依据的坚持，它会维持并升级为阻断——那正是它该做的。
   - 同一条意见最多来回两轮；两轮后仍有分歧，归入"需用户裁决"。
   - 如果 `send_message` 报 `active teammate "<id>" not found`，不要重试同一个 id：**自己按依据解决**——能由用户原话/台账/调查事实回答的补进草稿，只能由用户决定的问用户；**不得脑补证据替自己辩护**。
5. 申辩之后仍成立的意见才去见用户：逐条回报（接受并改／有理有据地驳回／回报用户裁决），并说明依据来自哪里。**不允许静默忽略任何一条。**
6. 报告结论为"不通过"或有未解决的阻断项时，修订草稿后**重新调用 `subagent_review` 新建复核者**（不复用——让同一个复核者看第二版，它会倾向于确认自己的意见被采纳）。**最多两轮**；第二轮仍不通过就停下，把未解决的问题整理给用户，不要无限循环。
7. 只有通过（或有条件通过且条件已解决）之后，才写出最终文件。写盘前提醒用户把 `/permission` 从 read-only 切回可写模式（例如 workspace-write），否则写入会被沙箱拒绝。

复核者只有 `read`/`read_image`/`glob`/`grep`，没有写权限，也不能向用户提问。所以它提出的"该由用户决定的事"必须由你转达给用户，不要自己拍板。

## 六、最终交付与三段闸门

写在会话工作区里，路径使用 `requirements/<项目名>-开发文档.md`（`requirements/` 不存在时创建）。除这份文档外不新增其他文件；写完后向用户报告确切路径，并说明可以继续补充修改。

交付后**不要开始实现**，而是提示用户走完剩下两道闸门：

| 阶段 | 在哪做 | 产物 | 闸门 |
|---|---|---|---|
| 1 需求确认（本会话） | 需求确认模式 | 这份开发文档 | 用户确认方向 |
| 2 计划 | 同一项目里的 plan 模式 | 经批准的实施方案 | 用户批准计划 |
| 3 实现 | 标准模式的新会话 | 可运行的代码 | 用户提出开发请求 |

要点：第 2 阶段把这份文档作为**输入**递给 plan 模式；第 3 阶段必须在标准模式（有 shell、可写工作区）里做。三段之间每一步都要用户明确点头，任何一段完成后都不要自动进入下一段。
