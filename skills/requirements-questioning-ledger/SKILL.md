# 提问方式与确认台账

## 一、提问方式

用 `ask_user_question`，不要用散文问。规则：

- 每轮 **1–3 个**问题，只挑最影响当前决策的。
- 每个问题给稳定 `id`（台账要引用它），把推荐项放首位并在标签末尾加 `(Recommended)`。
- 选项要具体到能直接改变设计，不要"要不要做得更好"这类伪选择。
- 需要用户自己填的内容用自由文本（`custom`），不要硬塞选项。
- 答案里的 `selected` 与 `custom` 是**唯一的"用户确认"证据**。没有这一步的，一律写进"技术建议"或"待确认项"，不得写成"已确认项"。

分工提醒：**调查员回答"机器是什么样"，你只能问用户"用户想要什么"。** 不要拿调查结果去替用户做产品决定。

## 二、确认台账

用 `todo_write` 把待确认项挂成清单，让用户在界面上看得见还没定的东西。每条至少包含：

| 字段 | 内容 |
|---|---|
| `来源` | 哪个问题 id / 哪一轮对话（真机事实写"调查员带回的命令与输出"） |
| `结论` | 用户选了什么，或自由文本原话 |
| `归类` | 已确认项 / 用户偏好 / 技术建议 / 待确认项 / 开发时决定 |
| `影响面` | 这个结论一旦改动，会连带影响文档的哪些部分 |

**已确认项必须有 `来源`**；整不出 `来源` 的，降级为技术建议或待确认项。台账里**不要美化**——把不确定的照样写出来，复核者才查得动。

## 三、信息分类（文档里必须分开）

| 类型 | 含义 | 文档中的处理方式 |
|---|---|---|
| 已确认项 | 用户明确同意的目标、交互或限制 | 核心要求 |
| 用户偏好 | 用户倾向的风格或方向，允许为实现效果微调 | 优先方向与设计依据 |
| 技术建议 | 你提出的候选方案 | 写清理由、代价与替代方案，不伪装成定稿 |
| 待确认项 | 会明显影响体验、成本、权限或工作量的未知项 | 列为需要用户决定的问题 |
| 开发时决定 | 不影响产品目标的内部实现问题 | 留给后续开发 AI 结合环境选择 |

## 四、阶段 D 的汇总清单

信息足够时，先给用户一份简明汇总，按下表逐项覆盖；**缺项要显式写"尚未讨论"，不要留空**：

1. 产品目标与非目标
2. 用户可见的核心界面与日常操作
3. 数据来源、权限、同步与失败时的表现
4. 设置项、菜单或托盘行为
5. 视觉方向与素材需求
6. 已确认项、用户偏好、技术建议、待确认项（四者分列）
7. 技术方向的理由与可替代方案

汇总后**只问一件事**：需要修改补充，还是确认按此方向整理开发文档。得到明确确认才进入文档产出。

产出草稿前，把台账连同草稿一起交给 `subagent_review`——它会专门核对"每条已确认项是否真能追溯到一次用户答复"，追溯不到的一律按阻断处理。
