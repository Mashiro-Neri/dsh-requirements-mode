# 交付前自检与落盘

顺序不能颠倒，尤其**不要在复核前落盘**。

## 一、自检清单

- [ ] "已确认项"每一条都能追溯到一次真实的用户答复（问题 id 或对话轮次）。
- [ ] 没有把自己的建议、默认假设或技术偏好写进"已确认项"。
- [ ] 四类信息（已确认项／用户偏好／技术建议／待确认项）彼此分开，没有混写。
- [ ] 每组模糊词（简单、实时、好看、轻量、自动）都有可观察定义。
- [ ] 权限、成本、稳定性、资源占用、隐私与失败行为，凡涉及者均已写。
- [ ] 主界面草图或表格已标注"讨论示意，非最终视觉稿"。
- [ ] 变更同步已核过：本轮改动牵动的其他小节都已一并更新。
- [ ] 文档结尾没有"接下来我开始实现"这类默认进入实现的表述。
- [ ] 已经过 `subagent_review` 复核，且报告里的每一条都有明确处理结论（接受／驳回／上报用户）。

## 二、落盘

复核通过（或有条件通过且条件已解决）之后才写文件：

- 路径：`requirements/<项目名>-开发文档.md`（`requirements/` 不存在时创建）。
- 除这份文档外不新增其他文件。
- 写盘前提醒用户把 `/permission` 从 read-only 切回可写模式（例如 workspace-write），否则写入会被沙箱拒绝。
- 写完报告确切路径，并说明可以继续补充修改。

复核环节本身的操作细节（怎么派活、怎么申辩、轮数上限）见 requirements-subagent-protocol 技能；这里不重复。

## 三、交付后的三段闸门

交付后**不要开始实现**，而是提示用户走完剩下两道闸门：

| 阶段 | 在哪做 | 产物 | 闸门 |
|---|---|---|---|
| 1 需求确认（本会话） | 需求确认模式 | 这份开发文档 | 用户确认方向 |
| 2 计划 | 同一项目里的 plan 模式 | 经批准的实施方案 | 用户批准计划 |
| 3 实现 | 标准模式的新会话 | 可运行的代码 | 用户提出开发请求 |

要点：第 2 阶段把这份文档作为**输入**递给 plan 模式；第 3 阶段必须在标准模式（有 shell、可写工作区）里做。三段之间每一步都要用户明确点头，任何一段完成后都不要自动进入下一段。
